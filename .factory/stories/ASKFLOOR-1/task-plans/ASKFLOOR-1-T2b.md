# ASKFLOOR-1-T2b — Default-allow risk table for gantry-native tools

## Problem
Gantry-native tools are judged by IDENTITY in `application/permissions/gantry-tool-risk.ts:59-166`: `gantryToolDefaultRisk(toolName)` maps a suffix to `low | medium | high` with no argument input, every namespaced-but-unknown suffix is HIGH (`:101-107`), `file` is HIGH by identity, every mutating `browser_*` tool is HIGH, and its only production caller `evaluateNativeRiskBranch` (`runtime/permission-classifier-native-risk.ts:6-21`, extracted by T2a, synchronous) receives `{ canonicalToolName, inputTruncated, yoloDenylistHit, requestFamily }` — never the arguments, although the classifier has built `classifierToolInput` just before (`permission-classifier.ts:302,331`). So in interactive auto a browser click, a virtual-store `file` list/read/write or a native file write inside the workspace asks (the routine "medium" tools such as `attachment_materialize`, canvas, render and memory writes already allow — `low` and `medium` both allow, `permission-decision-coordinator.ts:92-100`), while the OWNER RULING (decision 0155, spec AF-AC1) is the opposite posture: every gantry-native tool auto-allows by default and only a CLOSED set of high-risk rows asks. Two more gaps block the ruling: native `Write`/`Edit` never reach argument-aware logic because the eligibility gate (`application/permissions/permission-classifier.ts:11-28`) accepts only `Bash`/`RunCommand`, MCP names and bare gantry names — and the names that arrive from BOTH runners are the facade ids `FileWrite`/`FileEdit` (`shared/gantry-tool-facades.ts:64-76`); and the `file` host handler enforces no entry protection on `list`/`read` (`jobs/ipc-file-artifact-handlers.ts:109-175`), which the default-allow posture relies on.

## Scope / Non-goals
In: ONE small typed risk table replacing the identity model under the interactive auto lane (default LOW for every registered gantry tool; the closed high-risk rows; `ambiguous` for unknown names, malformed shapes of the two argument-shaped rows, raw-path browser file actions, artifact-sourced `file_upload` and the owner-ruled generic executors); host-side protected-entry enforcement in the `file` handler and the browser attach resolver (every mode, not lane-gated); the native-risk helper receives the arguments, the workspace root and the caller's lane, applies the table under `interactive_auto` and yields no native verdict under any other lane except the lane-independent `capability_run` HIGH guard (no legacy identity code survives); the eligibility gate widened for exactly the two native file-write facades; a prospective-write containment helper in the shared layer for native Write/Edit (browser raw-path file actions are ambiguous by owner ruling — no browser containment); host-side entry protection in the `file` handler's `list` and `read`; T2b table fixtures through the T1 harness. Out: rails (no row, no signal — T2a's `attachment_open` birthright already runs before the classifier), IPC `auto_strict`/`ask`/job verdicts (byte-identical, pinned), the inline live consult's code (`app/bootstrap/inline-agent-loop-tools.ts` untouched — it loses only the identity-based native allow and keeps its LLM consult; its 0121 gap is deferral D-0074), the LLM classifier prompt, the browser artifact policy's runtime behaviour (`browser-artifact-policy.ts` unchanged — the permission predicate mirrors its shape), decision memory (T3), the outage latch (T6), `deepagents-shell-filesystem-guard.ts`, `send_message` (0052 birthright in the rails; no destination-bearing variant exists — principle only), the AF-AC8 scenarios (owned by T1/T2a/T3c/T4/T6; T2b traces AF-AC1, AF-AC2 file half, AF-AC4 native-risk half, AF-AC7).

## Workflow

It starts after the deterministic rails (T2a's birthrights already ran) and stops at the native-risk verdict or the LLM consult; memory (T3) and the outage latch (T6) are other tasks.
