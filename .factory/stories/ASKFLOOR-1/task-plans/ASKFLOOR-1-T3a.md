# ASKFLOOR-1-T3a — Human-decision memory persistence

## Problem
Decision memory today holds machine verdicts and owner-authored kinds only: `permission_decision_memory` (`adapters/storage/postgres/schema/schema.ts:66-107`) has `kind ∈ {classifier_verdict, remembered_deny, trusted_root, standing_grant}` (`domain/ports/permission-decision-memory.ts:7-11`), a text `id`, no outcome, scope, scope key or acting person, and ONE unconditional unique key `(app_id, agent_folder, kind, lookup_identity)` (`schema.ts:97`) that the repository's single `put` upserts against and re-activates revoked rows on (`permission-decision-memory-repository.postgres.ts:33-78`). The story's decision 0154 needs a distinct HUMAN record kind: a person's remembered Allow or No, keyed per person and per scope, revocable by id, with a display-name snapshot — and a scope-key derivation that is OUTCOME-AWARE (a remembered Allow on a single-destination file write keys on tool + canonical destination with content excluded; a remembered No always keys on the full effect hash). Nothing consults or writes such records yet (T3b/T3c); T3a builds the storage, the scope keys, the host-owned service and the domain types they need.

## Scope / Non-goals
In: the schema change (new columns, the human-row CHECK, two partial unique indexes replacing the unconditional key) with its generated migration and drift-gate snapshot; the port and repository (typed `human_decision` kind, per-kind conflict targets, `putHumanDecision`, `listHumanDecisions`, `revokeById`, `countExactAllowsByTool`); ONE scope-key module; ONE application service `remember | list | revoke` over the port; the domain additions (`human_decision` decision source, the structured remember DTO, the provenance codec); an architecture note; Postgres integration and unit tests. Out: any consult or write from the coordinator, the inline runtime or the callback path (T3b/T3c); identity resolution of who tapped (T3c supplies `actingPersonId` + label; T3a persists what it is given and never resolves); job projection (T4); cards and `/permissions` (T5); the classifier-verdict cache semantics (unchanged, 0043/0155); `kind`/`place` MATCHING logic (T3b) — T3a only fixes their key FORMAT.

## Acceptance Criteria
- T3a-AC1: SCHEMA. `permission_decision_memory` gains nullable text columns `outcome`, `scope`, `scope_key`, `acting_person_id`, `acting_person_label` (physical snake_case — the table's existing convention; the deviation from the constitution's camelCase rule is recorded as deliberate in the migration note and the architecture note) and a CHECK `permission_decision_memory_human_row_ck`: `kind <> 'human_decision' OR (outcome IS NOT NULL AND scope IS NOT NULL AND scope_key IS NOT NULL AND acting_person_id IS NOT NULL)` (the label may be NULL — rows render "someone", 0154). The unconditional `permission_decision_memory_lookup_uq` is DROPPED and replaced by two partial unique indexes: `permission_decision_memory_lookup_uq` on `(app_id, agent_folder, kind, lookup_identity) WHERE kind <> 'human_decision'` and `permission_decision_memory_human_uq` on `(app_id, agent_folder, acting_person_id, scope, scope_key) WHERE kind = 'human_decision' AND revoked_at IS NULL`; the active lookup index stays. The migration is GENERATED (`npm run db:migrations:generate`, timestamp-named like `20260827174119_agents_web_ui_foundation.sql` — the currently live convention in `schema/migrations/`, not the retired `0107_`/`0110_` sequence) so the drizzle drift gate (`db:migrations:check`, `.github/workflows/ci.yml:63`) stays clean; the `meta/_journal.json` and snapshot travel with it. Human `id`s are UUID strings in the existing text column (no column type change). Tests (Postgres, `permission-decision-memory.postgres.integration.test.ts`, `schemaPrefix: 'permission_decision_memory'`): raw inserts prove (a) two non-human rows on the same four-column key still reject — the existing pin at `:154-175` is kept with its kind; (b) two ACTIVE human rows for the same person + scope + scope_key reject; (c) the same person + scope + scope_key with the first row REVOKED accepts a second row; (d) two different persons with the same scope + scope_key both insert; (e) a `human_decision` row missing any of outcome, scope, scope_key or acting_person_id rejects (one case each), and a missing label is accepted.
- T3a-AC2: PORT + REPOSITORY. `PermissionDecisionMemoryKind` gains `'human_decision'`; the row and put types gain optional `outcome?: HumanDecisionOutcome` (`allow | deny`), `scope?: HumanDecisionScope` (`exact | kind | place`), `scopeKey?`, `actingPersonId?`, `actingPersonLabel?` (closed typed enums exported from the port; no string literals elsewhere). The repository's generic `put` keeps today's conflict target for the non-human kinds and REFUSES `kind: 'human_decision'` (throws `HumanDecisionRequiresTypedWriteError`, a named domain error in the port — the human path has its own write). NEW `putHumanDecision(input)`: requires all four human fields (a missing one throws before any SQL — the same guard style as `assertPersistable`, `:17-34`), always `lookupIdentity = scopeKey`, `decision = outcome`, `provenance` from the codec (AC5), and upserts with the human partial index as the conflict target (`onConflictDoUpdate` with `targetWhere: kind = 'human_decision' AND revoked_at IS NULL`) updating `reason`, `acting_person_label`, `effect_hash`, `rail_version`, `effect_schema_version`, `created_at` — an active duplicate for the same authority is refreshed in place (one Forget still revokes the only active record, 0118); a revoked row is NEVER reactivated: the new write is a fresh UUID row and the revoked row stays as history. NEW `listHumanDecisions({ appId, agentFolder, actingPersonId, includeRevoked? })` ordered newest first, person-scoped (no cross-person rows, pinned); NEW `revokeById({ id, actingPersonId, nowIso })` → `'applied' | 'already_revoked' | 'not_found'` — `not_found` when the id exists for ANOTHER person (never crosses persons, pinned by a two-person test); NEW `countExactAllowsByTool({ appId, agentFolder, actingPersonId })` → `Record<toolName, number>` of ACTIVE `outcome = allow`, `scope = exact` rows grouped by the tool name carried in `principal` (the human row stores the request's `toolName` in the existing `principal` column — the trust-growth input read by T5a; documented in the architecture note). `getClassifierVerdict`/`putClassifierVerdict` are byte-identical. Tests: Postgres round-trips for each new method per person; unit guard test for the refusals.
- T3a-AC3: SCOPE KEYS in ONE module, NEW `application/permissions/human-decision-scope.ts`, pure and synchronous: `deriveHumanDecisionScopeKey({ outcome, scope, request, effectHash, workspaceRoot }) → { scopeKey: string; pathOnly: boolean } | undefined` with these rules. `scope = exact`: for `outcome = deny` the key is ALWAYS the full effect hash (`computePermissionEffectHash`, `domain/permission-effect-key.ts:48-99`, content included; `pathOnly: false`); for `outcome = allow` the key is `exact:path:<toolName>:<destination>` (`pathOnly: true`) ONLY when the request is one of the closed single-destination write shapes — `FileWrite`/`FileEdit` with EXACTLY ONE non-blank string destination among `file_path` and `path` (a dual-key input is not single-destination: full hash), `mcp__gantry__file` (any registered gantry spelling via `gantryNativeCanonicalToolName`) with `action: 'write'` → `(scope, path)` or `action: 'promote_scratch'` → `(targetScope, targetPath)` — and the destination is unprotected; every other allow keys on the full hash (`pathOnly: false`), so shell commands (redirects, `cp`, `mv`, `tee`, multi-target) are never path-only. Destination canonicalisation REUSES T2b's helpers, never re-implements them: native → `path.resolve(workspaceRoot, candidate)` after `evaluateProspectiveWriteBoundary` (`shared/permission-prospective-write.ts`) reports `inside: true` (outside, protected, hidden, secret, symlinked or an undefined root ⇒ NOT eligible ⇒ `undefined` for an allow — protected destinations never key an Allow; the same request with `outcome = deny` still keys on the full hash); virtual → `<normalizeFileArtifactScope(scope)>/<normalizeFileArtifactPath(path)>` (`domain/file-artifacts/virtual-path.ts`) unless `isProtectedArtifactEntry` (`domain/file-artifacts/protected-virtual-path.ts`) or `protected: true` ⇒ `undefined` for an allow; a malformed shape ⇒ full hash. `scope = kind`: key `kind:<categoryId>` where `categoryId` is the closed read-only category from T2a's `classifyPermissionEffectShape` (`shared/permission-effect-shape.ts`) or the facade identity for `WebSearch`/`WebRead` (`shared/gantry-tool-facades.ts`), or — trust growth, 0154 — `kind:tool:<toolName>` when the caller passes `trustGrowthTool: true`; a request with no closed category ⇒ `undefined`. `scope = place`: key `place:<canonicalRoot>` from the caller-supplied `canonicalRoot` (resolved by T3b via `resolveTrustedRootStage`; T3a only formats it) ⇒ `undefined` when absent. `outcome = deny` with `scope ≠ exact` ⇒ `undefined` (a No is always exact, 0154). When `effectHash` is undefined (incomplete input) every rule that needs it yields `undefined`. Tests (unit, exhaustive): each shape × outcome × scope, dual native keys, protected/outside/symlink destinations, changed-content near-miss (same path, different content: allow keys equal, deny keys differ), whitespace-padded virtual paths, missing hash.

## Technical Approach
1. **Schema + migration.** Edit `schema.ts` (columns, CHECK via `check()`, two `uniqueIndex(...).where(sql\`…\`)`), then `npm run db:migrations:generate` and commit the generated SQL + meta; hand-edit only the migration's leading comment (the deviation note). Rejected: a second table (0154 says one store; the coordinator reads one repository).
2. **Repository.** Add the typed methods; keep `put` for the four non-human kinds and make it refuse the human kind so the partial index is never hit by the wrong conflict target. Rejected: widening `put` with optional conflict targets (two write paths with one signature invite the reactivation bug 0118 forbids).
3. **Scope keys** pure over the request + T2b helpers (async only where `evaluateProspectiveWriteBoundary` is; the module exposes an async `deriveHumanDecisionScopeKey` and the service awaits it — the pure/sync claim in AC3 applies to everything except that one boundary call).
4. **Service** thin over the port; no lane logic (T3b), no identity resolution (T3c).
5. **Domain types** additive; `human_decision` source string added to the union and to any exhaustive switch the type-checker flags (the implementer lists them in the PR).
Naming follows the sibling convention (kebab-case, no dotted role suffix).

## Decisions
0154 (human-decision memory, generic scope — the primary spec: person-scoped, label snapshot, exact/kind/place, full-hash No, path-only Allow for single-destination writes, protected never learns an Allow, no reactivation of revoked rows), 0118 (person scope; one Forget revokes the only active record), 0107 (typed decision source — `human_decision` added to the codec, never string-inferred), 0054 (provenance distinct from risk), 0043 and 0155 (classifier cache untouched), 0121/0130 (unchanged; no consult here), 0138 (human acting person distinct from agent aliases — the service does not validate person kind; T3c passes a human person). No new decision. Orchestrator rulings on the seam map's open questions: fresh UUID row after revocation (history kept); T3c resolves and snapshots the person; canonical destination = resolved absolute path (native) or `<scope>/<path>` (virtual), dual native keys not eligible; the service owns id/clock injection; source value `human_decision`.

## Risks
Drift gate: a hand-written migration diverges from drizzle's snapshot — mitigated by generating it. Reactivation regression: the human path must never reuse `put`'s `revokedAt: null` update — pinned by AC1(c) and the `put` refusal. Cross-person leakage: every human read/revoke filters by `acting_person_id` — pinned by two-person tests. Key drift between T3a's destination format and T2b's judgment: the module imports T2b's helpers rather than re-deriving paths.

## Workflow
What moves through this task: one remember request (outcome, scope, person, request) from the service into a human_decision row, and one list/revoke request back out. It starts at the service boundary (T3c will call it) and ends at the table; consulting (T3b), projection (T4) and cards (T5) are other tasks.

```mermaid
flowchart TD
  R[remember dto: outcome, scope, person, request] --> G{guards}
  G -- blank person / allow_once --> N[not_rememberable]
  G -- ok --> K{scope key module}
  K -- deny + exact --> FH[full effect hash]
  K -- allow + exact + single unprotected destination --> PO[path-only key: tool + canonical destination]
  K -- allow + exact otherwise --> FH
  K -- kind --> KD[kind:category or kind:tool]
  K -- place --> PL[place:canonicalRoot]
  K -- protected / no category / no root / no hash --> N
  FH --> W[putHumanDecision: uuid id, lookup_identity = key, principal = toolName, provenance codec]
  PO --> W
  KD --> W
  PL --> W
  W --> U{active row for person + scope + key?}
  U -- yes --> UP[refresh in place]
  U -- no (none or revoked) --> NEW[fresh uuid row]
  L[list person] --> T[(permission_decision_memory)]
  V[revokeById person] --> T
  T --> RES[applied | already_revoked | not_found]
  C[countExactAllowsByTool person] --> T
```
