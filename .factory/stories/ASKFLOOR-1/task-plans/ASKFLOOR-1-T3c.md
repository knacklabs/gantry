# ASKFLOOR-1-T3c — Remember settlement and learning writes

## Context
T3a stores remembered decisions (#484) and T3b consults them (#486), but nothing writes one from a real card tap. Today every provider card tap carries a scalar mode (`allow_once | allow_persistent_rule | cancel`), the durable claim persists that scalar (`schema/worker-coordination.ts:171`, a plain `text` column), recovery reconstructs a decision from it, and the human-resolution paths apply the current request and record nothing. T3c makes a structured `remember { outcome, scope }` tap flow through the closed codec set, persist via `HumanDecisionMemoryService.rememberDerived` from a host-stamped context exactly once per claim, and apply the current request as a once-only approval — only when the host-stamped eligibility holds AND the lane re-derives `interactive_auto` from host facts at settlement (the story plan's rule; the lane needs no tool input). Seam map: `plans/exploration/askfloor-1-t3c-seam-map.md`; the round-1 grill (`askfloor-1-t3c-task-grill-answer.md`) and a follow-up exploration fixed the ownership, carriers, hook order and recovery path recorded below.

## Orchestrator rulings
1. **Durable representation:** a CLOSED set of four remember codes — `remember_allow_exact | remember_allow_kind | remember_allow_place | remember_deny_exact` — travels in the SAME slot that carries the scalar mode and is persisted verbatim in the claim's `claim_mode` text column. ONE application codec decodes a code (or a scalar) into `{ mode: PermissionApprovalDecisionMode; remember?: PermissionRememberResolution }`. The carrier types stay in `domain/types.ts` and widen LINE-NEUTRALLY: `PermissionRememberCode` is declared there on one line, `PermissionRecoveryEnvelope.renderedDecisionOptions` and `PermissionCallbackClaimIntent.mode` become `PermissionApprovalDecisionMode | PermissionRememberCode` on their existing lines, and the file's line count does not grow (join one existing two-line declaration) — no type move, no re-export. The Postgres prompt mapper validates BOTH `claim_mode` and every `renderedDecisionOptions` entry through the codec on read and refuses an unknown value (fail closed).
2. **Ownership:** T3c edits no file under `channels/` except the two codecs the story plan assigns it — `telegram/channel-shared.ts` (the longest code keeps a 36-character id within Telegram's 64-byte callback data) and `slack/permission-action-id.ts`; their shared parity owner is `test/unit/channels/provider-affordance-parity.test.ts`. Every provider handler and renderer is T5a's; until T5a no card emits a code.
3. **ONE host-derived `rememberContext`, attached BEFORE the prompt is awaited, no provider edit.** Because the durable request snapshot deliberately omits `toolInput`, no key can be derived at settlement or after a restart. The host derives, ONCE and asynchronously (`deriveHumanDecisionScopeKey` returns a promise), a validated `PermissionRememberContext` — declared in the NEW application module `application/permissions/human-decision-learning.ts` (application may import domain; domain must not know it): `{ eligible: boolean; laneInput: { permissionMode; hostJobId? }; lane; appId; agentFolder; canonicalTool; personId?; effectHash; effectSchemaVersion; railVersion; workspaceRoot?; kindVariant: 'category' | 'tool'; candidates: { deny; exact; kind; kindTool } }` where each candidate is T3a's own discriminated `HumanDecisionScopeKeyResult` (a refusal keeps its typed reason). T3c derives NO place candidate: the trusted-root canonical root is not exposed outside the coordinator, so `remember_allow_place` always resolves to `not_rememberable: no_root` until T5a exposes the root and adds the candidate. `kindVariant` is `'category'` in T3c. Provisional `eligible = lane === interactive_auto && personId non-blank (0118: the host stamps a person only for a DM) && !isScheduledJob`. IPC path: the member is created at `ipc-interaction-processing.ts:171` without context; the decision helper (`ipc-permission-classifier-decision.ts`, which holds the lane analysis, tool input and effect hash) derives the context and MUST await a caller-supplied `attachRememberContext(context)` — implemented by `ipc-interaction-processing.ts` over the existing `updatePendingInteractionPayload` (`domain/ports/worker-coordination.ts:344`, JSONB member payload, no migration) — BEFORE it awaits `requestPermissionApproval` (`:599`, inside which binding and the provider claim happen); the crash window between the provider claim and the helper's return therefore always leaves recovery a context. Inline path: `inline-permission-memory.ts` derives it before `runDurablePermissionInteraction` and it is persisted with the member at creation. Stage 2: `bindPendingPermissionInteractionMessage` finalizes `eligible = context.eligible && matchKind === 'individual'` for every member it binds (a coalesced batch, `permission-approval-requester.ts:347`, ends ineligible). Settlement on every path (IPC, inline, recovery) reads ONE typed accessor, `rememberSettlementForClaim(claim) → { context: PermissionRememberContext; resolution: { mode; remember? } } | null` in `pending-interaction-permission-callback.ts` (context validated via `parsePermissionRememberContext`, the raw claimed value decoded through the codec, both from the same claimed row), and re-derives ONLY the lane, from the context's persisted `laneInput` through `deriveAutoLaneAnalysis` (the story plan's "re-derives" rule; deterministic on every path, recovery included) — it must equal `interactive_auto`; no key is ever re-derived.
4. **Write-then-apply, fail-open (the story plan's order, `:160`, `:192`):** learning runs BEFORE the current request is applied, through the existing seams — IPC in `ipc-interaction-processing.ts` just before `applyPermissionInteractionDecision` (`:269`), inline in the existing `afterDecision` hook (`inline-agent-loop-tools.ts:483-543`, which runs before `finishDurablePermissionInteraction` applies), recovery in `pending-interaction-permission-callback.ts` just before the recovered apply (`:491`) — and it NEVER throws: a refusal or port failure logs one `warn` (`unlearned`) and the current request is applied as a once-only tap. Crash after learning, before application or settlement → recovery learns again → T3a's refresh keeps one active row; `already_decided` never reaches learning. No new hook.
5. **The write bypasses derivation:** `HumanDecisionMemoryService.rememberDerived(dto)` with `dto = { appId, agentFolder, actingPersonId, actingPersonLabel?, canonicalTool, outcome, scope, scopeKey, pathOnly, effectHash, railVersion, effectSchemaVersion, reason }` shares `remember`'s write path (refusals, id, provenance, `putHumanDecision`) with the key supplied instead of derived. Candidate selection from a decoded code: `remember_deny_exact` → `candidates.deny`; `remember_allow_exact` → `candidates.exact`; `remember_allow_kind` → `candidates.kind` when `kindVariant === 'category'`, `candidates.kindTool` when `'tool'`; `remember_allow_place` → `not_rememberable: no_root` in T3c (no place candidate); a refused candidate → `not_rememberable` with its persisted typed reason.
6. **Person:** the acting person is the context's host-stamped `personId` (never a callback identity); label `undefined`. Blank person ⇒ `eligible` is false ⇒ nothing persists.
7. **Composition root:** recovery's `learn` dependency is threaded through `pending-interaction-durability.ts:47` and configured where the durability backend is built, `adapters/storage/postgres/runtime-store.ts:127`, over the decision-memory repository; the IPC settlement helper (`runtime/permission-remember-settlement.ts`) and the inline module use the same application helper; one production-wiring case in `test/unit/storage/runtime-store.test.ts`.
8. **Authorization is untouched:** an unauthorized tapper is rejected before the claim exactly as today (`pending-interaction-permission-recovery-orchestrator.ts:88`, 0118) — no claim, no write, no application; an AUTHORIZED tapper whose code lands on a remember-ineligible card settles the decoded scalar base once with no memory write.
9. **Carrier consumers:** besides the two `types.ts` fields, `pending-interaction-prompt-binding.ts:119,165` and the control API `control/server/session-interaction-approvals.ts:234,256` consume rendered and claimed modes; both decode through the codec. The control API stays SCALAR-ONLY in T3c: it maps a remember code to its scalar base for display and never accepts a code on its POST (a control-surface remember affordance is a later task); no route change.

## Scope / Non-goals
In: codec module; the line-neutral carrier widening; the two owned codecs; the durable path (member payload stamp, claim carries the code, prompt mapper validates on read, recovery decodes and learns); ONE learning helper; the IPC settlement helper; the inline post-apply call; the S2 fixture through the real claim/application/learning path. Out: every provider handler and renderer, card buttons and copy, AND the four-provider forgery matrix (unauthorized / ineligible / double-delivery per provider) — T3c proves the shared durable seam only; that matrix is assigned to T5a with the provider files (T5a); job projection (T4); `/permissions` (T5b); the outage latch (T6); anything T3b consults.

## Technical Approach
1. Codes ride the existing mode slot end to end; the carriers widen in place, line-neutrally. Rejected: a type move (19 unscoped importers), a structured claim column (migration) and an opaque token (needs a lookup recovery cannot rebuild).
2. One host-derived context, bound at prompt time, carries eligibility and every candidate key; one learning helper consumes it; the three callers are thin and run before application (story plan order).
3. Eligibility lives in the persisted context; forged or replayed codes degrade to their scalar base behind the existing claim guards (`pending-interaction-permission-claim.ts:40-60`, `-callback.ts:359-397`).
4. Idempotency comes from T3a's refresh semantics; no new ledger.

## Workflow
At prompt time the host derives one remember context (candidate keys + provisional eligibility), attaches it to the durable member, and the binding finalizes eligibility from the real match kind. A tap carries a scalar or one of the four codes; the codec decodes it; the claim persists it once; the learning helper writes from the context (fail-open); then the current request is applied exactly as a once-only tap. Recovery replays the same code through the same pre-apply point.

```mermaid
flowchart TD
  H[prompt time: host derives rememberContext, persists on member payload] --> T[tap: allow_once / cancel / remember_*]
  T --> P[codec: decode]
  P --> C[claim once: claim_mode = value]
  C -- already_decided --> X[settle, no write]
  C -- claimed --> E{context.eligible AND candidate for the scope?}
  E -- no --> A[apply current request once-only]
  E -- yes --> L[learnRememberedDecision -> service.rememberDerived, never throws] --> A
  RC[restart: recovery decodes claim_mode, reads context] --> E
```
