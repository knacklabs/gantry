# JOBPERM-2-T2 — Once expiry settlement + Postgres integration proof

Contract (AC5 + AC2-INT of `plans/active/JOBPERM-2-job-permissions-one-card-path-with-rule-once-grants.md`): a `once` need whose run ended before a decision (its waiters are all dead or expired) settles as expired — never handed off to a later run, never durable authority — and the card row reads "Expired — the run ended before a decision; it will ask again next run". A Postgres integration test proves the once chain end to end: signed scheduled request → once need → Allow → signed `allow_once` replay to the runner, no rule row written. Rule rows, provider renderers, runner, heartbeat, schema untouched.

Steps:
1. `apps/core/src/application/interactions/job-permission-reconciler.ts` waiter sweep (~`:259–306`): when every waiter of a need is dead/expired, a `rule` need goes to `handoff_pending` as today; a `once` need (`need.grant === 'once'`) goes to `cancelled` with `need.decidedBy` left unset and a new optional `need.expiredAt` (ISO) so the card can tell "expired" from a human deny. The `handoff_pending` → `handed_off` path and rerun barriers must never see a once need (guard in `mutateExisting` where handoff is resolved, ~`:323–335`). An expired once need never replays and never calls `persistGrant`.
2. Row copy: `apps/core/src/domain/job-permission-card-actions.ts` renders a cancelled once row with `expiredAt` as "<label> — Expired — the run ended before a decision; it will ask again next run" (AC5 sentence verbatim after the label); it is not decisionable (no Allow/Deny applies to it). `job-permission-card-projection.ts` carries `expiredAt` on the row snapshot; `domain/ports/job-permission-durability.ts` adds the optional field to need + row shapes (JSONB record, absent = not expired; A-0065).
3. A later run raising the same request shape creates a fresh once need (request-id identity guarantees this) — assert in a unit test that the expired need is not reused.
3b. Pipes never get leaf rules (owner ruling 2026-08-27, decision 0134): in `apps/core/src/application/permissions/permission-suggestion-synthesis.ts` (~`:71–84`), after `parseBashCommand`, return no persistable rules when `parsed.piped` is true — the matcher (`shared/tool-rule-matcher.ts:389`) never honours per-leaf rules for a piped command, so proposing them would save useless rules and make a job ask again every run (and offer chat an "Allow for future" that never works). Consequence: every piped RunCommand attaches as a `once` need. Unit test in `apps/core/test/unit/application/permission-suggestion-synthesis.test.ts`: a piped command yields no rule suggestions; a `&&` compound still yields per-leaf rules.
4. Integration: `apps/core/test/integration/permission-decision-chain.postgres.integration.test.ts` — add `it('completes the signed once-card chain for a job request with no persistable rule without writing a rule')`: scheduled request with `jobId` and a piped RunCommand (no persistent rule suggestion) → `attachRequest` creates a once need + card revision → Allow via the provider action → reconciler applies → runner receives signed `allow_once` (`decidedBy: human_once`, `updatedPermissions` null) → no permission rule row written; mirror the scaffolding of the existing signed allow-once test (`:414`) and allow-for-future test (`:490`).
5. Tests (implementer writes): `apps/core/test/unit/application/jobperm-durability.test.ts` — `it('settles a once need as expired when its run ended')` (required test, exact leaf name) + the no-reuse assertion; `jobperm-edges.test.ts` — expired row copy and non-decisionable; existing rule handoff tests unchanged.
6. Verify: `npx vitest run -c vitest.unit.config.ts apps/core/test/unit/application/jobperm-*.test.ts`; `npx tsc --noEmit`; `npm run check:architecture`; `GANTRY_TEST_DATABASE_URL=postgresql://gantry_app:496582611f01121be59b03a008e2cc39@127.0.0.1:5432/gantry_test npx vitest run -c vitest.integration.config.ts apps/core/test/integration/permission-decision-chain.postgres.integration.test.ts` (or the repo's `npm run test:integration:postgres` lane).

Not in scope: rule-row handoff semantics; provider renderers; runner/heartbeat; setup-pause path.
