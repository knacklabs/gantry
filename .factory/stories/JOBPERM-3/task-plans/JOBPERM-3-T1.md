# JOBPERM-3-T1 — Retire outcome on the card revision + Telegram delete/receipt

Contract (AC1 Telegram part, AC2, AC3, AC4 of `plans/active/JOBPERM-3-settled-job-permission-cards-disappear-like-chat-prompts.md`, amended after signal S-0041): when the job permission card retires (no visible rows left), the shared projection records the outcome on the revision — `allowed` (every row allowed) or `expired` (remaining rows expired). A card whose rows were all allowed is deleted on Telegram (receipt edit if the delete fails); an expired card is edited to per-row "Expired: <label>" lines and never deleted. A DENIED row stays a live card row with one-tap Reconsider (decision 0144), so a card containing a Deny never retires — there is no "denied" retire outcome. The deleted/receipt state is recorded so a retried retire revision no-ops. Existing suites pass with only retire-text/operation assertions updated.

Steps:
1. Revision shape (`apps/core/src/domain/ports/job-permission-durability.ts`): on `JobPermissionCardRevision` add `retireOutcome?: 'allowed' | 'expired'`, `retiredRows?: Array<{ label: string }>` (the expired needs), and `retireDelivery?: { deletedAt?: string; receiptMessageId?: string }` (JSONB record; absent = legacy retire; A-0065). The Postgres need repository (`apps/core/src/adapters/storage/postgres/repositories/job-permission-need-repository.postgres.ts`) copies these fields into the delivery payload verbatim.
2. Projection (`apps/core/src/application/interactions/job-permission-card-projection.ts` ~`:155`): when `operation === 'retire'`, derive the outcome from need state — `expired` if any settled need is `cancelled` with `expiredAt`, else `allowed`. `livingCardNeeds` keeps `denied` needs live (unchanged), so a denied need never reaches retire. Never derive from text.
3. Shared text (`apps/core/src/domain/job-permission-card-actions.ts:70`): `retire` + `allowed` ⇒ "Approved — this job's permission requests are done." (fallback only); `retire` + `expired` ⇒ one line per retired row: "Expired: <label>". Legacy retire (no outcome) keeps today's line. Actions stay empty.
4. Wiring (`apps/core/src/app/bootstrap/job-permission-wiring-setup.ts` ~`:315`): a retire revision with `retireOutcome === 'allowed'` and a `providerMessageId` is delivered with a new `MessageSendOptions.deleteMessageId` (next to `replaceMessageId`, `apps/core/src/domain/types.ts:545`) plus the receipt text as fallback content; `expired`/legacy stays `replaceMessageId`. `apps/core/src/domain/messages/retry-tail-provider-payload.ts` keeps the new `jobPermissionCardRevision` fields through the durable sanitizer.
5. Telegram (`apps/core/src/channels/telegram/channel-delivery.ts` zero-affordance branch ~`:114–190` and `job-permission-card-delivery.ts`): on `deleteMessageId`, inside the existing per-message lane (`deliveries.serialize`), short-circuit if `retireDelivery.deletedAt`/`receiptMessageId` is set; else `bot.api.deleteMessage`; on failure `editMessageText` with the receipt text and empty keyboard (same shape as `permission-prompt-settlement.ts:82–101`). Record `deletedAt` or `receiptMessageId` via the existing `deliveries.record` path; the reconciler's 'Job permission card delivered' log line carries `operation: 'delete'`.
6. Tests (implementer writes): `apps/core/test/unit/application/jobperm-durability.test.ts` — `it('deletes a fully allowed card on retire and falls back to a receipt edit')` (required, exact leaf name), retire with an expired once row ⇒ "Expired: …" edit and no delete, a card with a denied row does not retire, retried retire after `deletedAt` ⇒ no provider call; `jobperm-edges.test.ts` — outcome derivation; `apps/core/test/unit/domain/messages/retry-tail-provider-payload.test.ts` — new fields survive; `apps/core/test/unit/channels/telegram.test.ts` — delete/fallback delivery; `apps/core/test/unit/adapters/` — Postgres payload carries the fields; Postgres `apps/core/test/integration/permission-decision-chain.postgres.integration.test.ts` — the allowed once chain ends with a delete delivery recorded. Update assertions expecting "All permission requests for this job are settled." only where the new outcome applies.
7. Verify: `npx vitest run -c vitest.unit.config.ts apps/core/test/unit/application/ apps/core/test/unit/channels/telegram.test.ts apps/core/test/unit/domain/ apps/core/test/unit/adapters/`; `npx tsc --noEmit`; `npm run check:architecture`; Postgres lane host-side (orchestrator).

Not in scope: Slack/Discord/Teams deliveries (T2), chat prompts, card behaviour while rows are open, once-expiry rules, any "denied" receipt.
