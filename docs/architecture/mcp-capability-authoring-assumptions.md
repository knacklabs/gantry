## Consolidated binding-set fence

The fence covers MCP binding-set membership as well as fields. `listAgentBindings` without a caller limit is the internal complete-set query. Every Postgres bind, unbind, and desired-state replacement locks the owning agent row before mutation, and fenced replacement compares the complete live id-and-field set under that same lock. A concurrent addition, removal, or change therefore either causes a retry or waits until replacement completes; disabled history beyond 500 rows cannot be omitted. Postgres repository tests pin unexpected-row rejection, the shared writer lock, and a 501-row unbounded read.

A proposal mirror snapshots every configured agent's complete MCP binding set before publishing its full settings revision. The persisted metadata includes the explicit fenced agent ids separately from the rows, so an agent whose reviewed binding set is empty is still protected against a concurrent insertion; both persistent-rule addition and removal pass that explicit configured-agent set. Desired-state reconciliation checks the complete multi-agent snapshot while planning replacements only for agents that satisfy the existing authoritative-or-configured-capability predicate. It commits those agent upserts plus capability replacements through one Postgres transaction; non-authoritative omitted capability sets remain untouched, and no later agent update occurs until the fence passes. Grant/revoke mirroring starts from the latest revision and refreshes only MCP source fields that still match that revision's own fence, so a not-yet-applied disable, removal, addition, or narrowing is preserved into the successor. If any covered binding set changes after the conditional revision append but before local projection, the importer appends a fenced compensating successor containing the previous capability selection and the current complete MCP projection before returning the rejection. Each in-flight MCP proposal selection carries an internal grant token keyed from the exact post-mirror capability id and version in revision metadata; ordinary successors inherit it, and a later human reapproval replaces it. Recovery removes only selections still carrying the failed token, so it cannot erase a later approval of the same deterministic capability id. A concurrent successor is not assumed safe: recovery rebases on its latest document, preserves unrelated edits, and refreshes only source status/scope fields that still match that successor's own stored fence. Pending source edits therefore survive stale live projection while unchanged fields converge to current authority. Equivalent recovery successors are consumed idempotently instead of producing one revision per worker. Runtime source materialization also uses the same unbounded binding query. Desired-state, settings-import, restart-sync, and runtime authorization tests pin those convergence cases.

Once a revision head carries an MCP authority fence, every successor refreshes and carries that fence even when its caller did not supply proposal metadata. This applies at the direct fleet append boundary as well as workstation projection sync, preventing an unrelated settings write from silently returning the revision stream to unfenced replay.

The revision document, revision-local grant provenance, complete fenced agent set, and projected capability bindings form one ordered authority transition. Workstation and direct fleet imports first project the current MCP binding status/scope into unchanged source fields, restore only source edits that differ from the caller's revision base, and then append the matching live fence. Successors union the prior fenced agent ids even when an authoritative document has removed those agents. Same-path concurrent array or scalar edits fail as a visible settings conflict instead of dropping either side. Authoritative removal includes every removed fenced agent as a disabled agent plus an empty capability replacement in the same locked batch. Crash replay loads the predecessor revision and the failed revision's grant tokens, so compensation removes only a selection carrying the exact in-flight token while preserving tokenless, older, or later selections. Settings-import, watcher, desired-state, and crash-replay tests pin each part of this transition.

Revision consumers treat a stale persisted fence as recoverable authority drift, not a permanent startup or listener failure. Workstation revision-authority boot, fleet boot, and the live fleet revision listener append a conditionally fenced successor from the current complete binding projection and retry the latest revision; they never apply the stale source document unfenced. Settings-import and listener recovery tests pin preservation of an already-approved capability while a concurrently disabled source remains disabled and advancement to the recovered successor revision.

If reload fails after a desired-state reconcile, compensating rollback never reapplies the approval's stale source snapshot. It snapshots the current complete binding set, projects that exact current status/scope into the previous settings document (explicitly disabling configured sources absent from the live set), and reconciles under the same snapshot fence. A concurrent revoke or narrowing therefore either survives rollback or changes the fence and rejects it.

MCP grant publication is not callable while its durable mirror is unsettled. Approval holds an exclusive source-definition lock through catalog persistence, binding activation, settings revision append, local projection, and rollback. Call-time authorization acquires the matching shared lock before reading selected capability bindings, so it observes either the completed grant or the completed rollback. If any step fails after the approval revision was appended, recovery uses the grant's revision-local provenance token to publish a compensating successor before the approval returns failure; restart cannot replay the rejected selection. Matching-revision file reload uses the same stale-fence recovery loop as boot and the revision listener. Concurrency, reload-failure replay, watcher, boot, and listener tests pin this publication boundary.

Conversation and thread fields on an MCP source binding are authorization scope, not display metadata. Proposal synthesis uses the authenticated canonical conversation route, and source inventory plus call-time authorization filter the active binding against that same route. Global bindings remain available across the agent; conversation- or thread-scoped bindings fail closed when canonical route context is absent or mismatched. Durable async MCP work carries the canonical authorization route in its encrypted execution payload so recovery rechecks the same scope before calling. Candidate and proxy tests pin cross-conversation and cross-thread denial.

The long approval transaction locks MCP definition rows with `FOR NO KEY UPDATE`: definition/status changes remain excluded, while concurrent binding inserts may take their foreign-key key-share locks without inverting the agent-row-first binding-writer order.

Administrative rebinds resolve the existing row with an exact app-agent-server lookup rather than a paginated binding list, then preserve its required flag, permission policies, source scope, conversation route, thread route, and creation time unless the caller explicitly replaces a supported field. Rebinding therefore cannot widen an older source or erase route restrictions merely because it fell outside a list page.
