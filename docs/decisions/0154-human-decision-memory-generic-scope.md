# Human-decision memory with generic scope, consulted before the classifier in interactive auto

## Context
`gantry.permission_decision_memory` today stores only classifier verdicts, and the writer rejects human `allow_once` outcomes; a human's Allow is used only as prompt-hint text for the next classifier call. On 2026-09-02, 975 of 976 decisions in 48 hours were `allow_once`, so the owner tapped the same reads again and again. The owner ruled that a tap must teach the system ("[Allow] = remembered, the default; [Just this once] = not learned; [No]"), that what is remembered is a GENERIC scope rather than one exact command, with a broadest-safe default, and that learned decisions must be visible and revocable. Decision 0040 already names once / this-folder / standing scopes; 0043 keeps deterministic facts in the rails and risk in classification; 0121 forbids the classifier on autonomous runs.

## Decision
A human **[Allow]** or **[No]** in the interactive auto lane is recorded as a distinct memory record kind, `human_decision`, with an `outcome` (allow | deny), keyed by the exact effect hash + rails version and carrying a **scope**: `exact` (this action — for a remembered ALLOW on a single-destination file write, tool + canonical path with content EXCLUDED: the owner ruled on 2026-09-02 that a remembered Allow authorizes future content to that path; a remembered NO always keys on the full effect hash including content, so different future content asks again; protected paths never learn an Allow), `kind` (a closed category of action, initially {read-only shell/file reads, web searches and page reads}, matched by the verb/argument read-only classification WITHOUT the trusted-root check), or `place` (anything of that kind under a canonical root, reusing `resolveTrustedRootStage` as the store — no second root store). The default scope when the owner does not choose is the broadest SAFE one: `kind` for read-only asks, `exact` for writes and destructive asks; a remembered **[No]** always has `exact` scope (a broad remembered refusal would silently fail later work with no card); destructive asks (delete/overwrite/force shapes) can remember ONLY a No — a destructive Allow is never learned and the card offers no remember button for it; every record carries the resolved acting person and a snapshot of their display name at decision time (decision 0118) and is consulted only for that person's requests — this AMENDS 0118's unresolved-identity rule ("shared grant; no downgrade", 0118 §45-47) for `human_decision` records only: when the host cannot resolve who tapped, nothing is remembered and the tap acts as Just-this-once (owner ruling 2026-09-02: no shared group memory); group/channel requests carry no memory person (0118 §40-47), so in groups there is no remembering at all — cards carry no human-decision-memory controls or copy (today's labels and durable-rule controls stay exactly as they are), nothing is written or consulted, and learning stays a DM feature until a separate decision introduces a trusted group actor (owner ruling 2026-09-03); an exact remembered No is checked before everything else — hard restrictions included — so a repeated protected-path or destructive ask the owner already refused stays silent, while remembered Allows are consulted only after the non-overridable rails and protected destinations never learn an Allow; remembering controls and their copy appear only on cards the host stamps as eligible (a DM request in the interactive-auto lane with a resolved person); ask, auto_strict, job and group cards keep today's shape and controls unchanged (existing durable-rule approvals included) — only human-decision learning and consultation are off there; an eligible card states the scope before the tap ("Allow will remember: …", "No will remember: this exact action.") and offers exactly one alternative remembering button (a narrower place, or the CARDSIMPLE-1 family rule when one applies). The memory is consulted before the classifier in interactive auto only — exact, then kind, then place; an allowed match auto-allows with `decidedBy: human_decision`, a denied match keeps the deny. **[Just this once]** keeps today's `allow_once` semantics and is never written; coalesced batch cards (Allow all / Deny all) are once-only and never write memory — only individually reviewed cards remember (owner ruling 2026-09-02). A rails-version bump or an owner "Forget this" (`revoked_at`) invalidates a record and the next ask says why. Ask mode and auto_strict never consult the memory; scheduled jobs consult it only as projected declared grants (decision 0153). This decision also AMENDS 0052 and 0121 (owner ruling 2026-09-02): opening an attachment already present in the conversation (`attachment_open` with a host-validated opaque id) is an input-gated birthright in the deterministic rails in EVERY permission mode — it joins 0052's self-surface birthright set, and 0121's "an undeclared grant denies" rule gains exactly this one birthright exception; a malformed id asks, an id that fails host origin validation is not a permission question (not-found line, never a card).

## Consequences
- Taps become teaching: after one remembered Allow for a read, reads of that kind stop asking anywhere; writes and destructive actions only ever learn the exact action.
- Learned authority is inspectable and reversible: `/permissions` shows the ten newest active records (outcome, scope, when, by whom, and any job that actually used it) with per-row "Forget" buttons; `/permissions all` lists every active, current-rails record with a short id and `/permissions forget <id>` revokes any of them (owner ruling 2026-09-03).
- Rejected alternative: exact-hash-only learning — it cannot end the tapping for shell-heavy work (every command shape would ask once) and would have kept the owner's complaint alive.
- The attachment birthright is the story's only deterministic-rails edit; it is pinned by per-mode rails tests.
- Doors closed: no learning from ask mode, auto_strict, or jobs; no other widening of the shared deterministic rails (the kind match lives on the memory side of the coordinator, after the rails fall through); the memory repository is the only writer.
- Work implied: a migration adding `scope`/`scope_key` beside the existing columns, repository tests, an architecture note for the record kind, coordinator consult + the two human-resolution write points, invalidation on rails-version bump.
