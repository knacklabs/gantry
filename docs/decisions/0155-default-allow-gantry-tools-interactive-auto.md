# Gantry-native tools auto-allow by default in interactive auto; only a closed high-risk list asks

## Context
`gantryToolDefaultRisk` (`application/permissions/gantry-tool-risk.ts:98`) short-circuits gantry-native tools with static buckets hard-coded to HIGH — every `send_message`, every `browser_*` mutation, scheduler and admin mutations, `file`, and every unmapped tool — so those tools always ask in auto mode and the classifier never judges them. That conservative posture dates from #212 / decision 0043 ("risk in classification, deterministic facts in rails") when the classifier was new. The live evidence of 2026-09-02 (ten taps in three minutes on reads; three taps to read an attachment) and the owner's bar ("behave like Claude Code auto mode") led the owner to rule on 2026-09-03: "auto-allow most of the gantry tools by default, including the browser; focus on simplification; unless high risk, auto allow the tools", and to name the high-risk set.

## Decision
In the interactive auto lane every gantry-native tool is LOW by default and auto-allows with typed provenance — all `browser_*` actions (status, inspect, navigate, click, type, press, select, evaluate, upload, dialogs, tabs, screenshot, wait), `file` list/read (entry protection enforced host-side), scheduler and admin READS, attachment tools. Only a CLOSED high-risk list stays HIGH and asks: (1) destructive or protected writes — native Write/Edit outside the agent workspace or on a protected/secret path (prospective-write containment, symlinks rejected); `file` write/promote_scratch to a protected virtual path or with `protected: true` (unprotected writes to the agent's own virtual store are LOW — it is the agent's store); any browser file action whose payload source is a raw filesystem path — `file_attach` with a path, or `file_upload` with `source: { type: "path" }` (today that source form bypasses the raw-path rejection and resolves like attach, `adapters/browser/browser-artifact-policy.ts:57-98,132-145`) — outside the workspace, protected or secret; artifact-sourced `file_upload` stays LOW; (2) scheduler mutations — the registry's canonical scheduler-mutation set (`shared/admin-mcp-tools.ts:32-39`: create/update/delete and pause/resume/run-now); (3) admin mutations — the registry's canonical admin exports (`shared/admin-mcp-tools.ts:129-159` settings, permissions, agents, authority-changing, dispatcher, decision-actor; `DELEGATION_DISPATCHERS` at `:172-177`). The table IMPORTS those sets rather than restating them. Messaging to a destination that is not one of the agent's own registered channels is HIGH by principle (the owner named it), but no destination-bearing `send_message` exists today (`runner/mcp/tools/messaging.ts:385-429` always targets the agent's own surface; decision 0052 birthright stays), so it is not a table row and any future destination-bearing variant requires a new decision. Anything the table cannot classify — unmapped tools, or a shape that fails the tool's own schema validation — is `ambiguous` and goes to the classifier; nothing is forced HIGH by identity any more. The posture is ONE small typed risk table with an exhaustive per-tool test. It applies to interactive auto only: the shared deterministic rails, ask mode, auto_strict and scheduled jobs (0121) are untouched.

## Consequences
- Re-calibrates 0043's static buckets (and the #212 posture) from "ask unless proven safe" to "allow unless on the high-risk list"; 0043's split — deterministic facts in rails, risk in classification — is preserved because the table is a deterministic fact and ambiguity still goes to the classifier.
- The closed browser verb matrix and per-argument `file` risk planned earlier are dropped; simpler code, one table to review.
- Browser network side-effects — navigation, clicks, form submission, payments and credential entry — are NOT on the high-risk list by explicit owner choice (offered and declined on 2026-09-03); this decision therefore AMENDS decision 0052's browser reading (its shell-egress and secret floors, `0052:56-57`, stay untouched). One browser action IS high risk through the protected-writes row: `file_attach` whose payload source is a raw filesystem path outside the workspace, protected or secret (exfiltration of a secret is a protected-path effect); `file_upload` is artifact-based and LOW. If the choice proves wrong the list grows by one row and a test, never by reverting the posture.
- `file` is judged by a discriminated per-action predicate over its complete callable contract (list: scope + optional path/limit; read: artifactId + version OR scope + path, + offset/readLimit; write: scope + path + content + optional encoding/contentType/protected; promote_scratch: source path + targetScope + targetPath; anything else ambiguous), because its single schema permits every optional field; virtual-path protection is a different check from filesystem containment.
- Every auto-allow is visible through typed provenance on the decision and the permission audit trail; `/permissions` (decision 0154) remains the human-memory ledger and does not list auto-allows.
- Doors closed: no widening of the shared rails; no change to ask, auto_strict or job semantics; the high-risk list is closed and reviewed, not heuristic.
