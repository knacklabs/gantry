# ASKFLOOR-1 — The judge actually judges: context-aware asks in auto mode

Story: ASKFLOOR-1
Inputs: owner directive 2026-09-01 ("the classifier is supposed to judge unknown commands automatically and move only when needed") plus two sol@xhigh validation passes — the original first-ask validation (plans/exploration/askfloor-1-validate.md, six findings folded) and the 2026-09-01 auto-mode-parity gap hunt (plans/exploration/classifier-automode-consolidated.md, three passes). Live diagnosis: the classifier DOES judge unknown shell commands (auto-allowing low/medium), and complete `send_message` calls are ALREADY birthright-allowed before any risk bucket (decisions 0052/0121). The remaining pain is threefold: (a) static `high` defaults for whole tools skip the classifier; (b) a human's Allow is NOT learned, only used as prompt-hint text, so identical requests can re-ask; (c) a deterministic read-only gate cannot prove several structurally read-only cases.

## Relationship to the sibling stories (owner 2026-09-01: one program)

The "judge decides; the human is asked only when needed" program spans three stories, kept scope-disjoint:
- CARDSIMPLE-1 (landed): family rules eliminate REPEAT-asks for grantable commands; rails-before-family ordering added the one coordinator branch. ASKFLOOR-1 depends on its landed state and adds the family rail-hit path to its invariance suite.
- ASKFLOOR-1 (this story): eliminates needless FIRST-asks (arg-aware native risk) AND makes human decisions STICK for shapes that can't hold a family grant (decision-learning). Touches only the caller-side native-risk inputs to `gantryToolDefaultRisk` and an auto-only human-decision memory consulted before the LLM — NEVER the shared deterministic rails/read-only gate, NEVER the family-synthesis machinery.
- SHIMPIN-1 (new sibling, NOT this story): package-pinned runner-shim families (`npx <pkg> *`) so shim commands can hold a durable grant. Lives in family-rule-synthesis/bash-command-parser — CARDSIMPLE-1 machinery territory, explicitly out of ASKFLOOR-1's scope. Cross-referenced because ASKFLOOR-1's decision-learning is the fallback for shims until/unless SHIMPIN-1 lands.
- CARDSIMPLE-2 (sibling): the card surface (explain-on-exclusion, settle/retract lifecycle).

## Why

In auto mode the owner should meet the permission system only when something genuinely needs a human — and never twice for the same decision they already made. Today provably harmless actions still interrupt (the static risk map rates whole tools, not actions), and a human's approval is forgotten (used only to bias the next LLM verdict), so identical requests — especially a scheduled job's per-run shim/pipe commands — re-ask every time.

## Behaviour

### 1. Human decisions are learned and consulted before the judge (auto only) — NEW, highest impact
#### Owner rulings 2026-09-02 (ledgered requirements rounds)
- **What a tap means.** The card offers three choices: **[Allow]** — remembered (the default, rendered bold); **[Just this once]** — NOT learned, expires with the run exactly as today's allow_once (decisions 0040/0043 hold: a once-only decision is never reusable); **[No]**. The remembered outcome is the default, which is what makes the owner's taps teach the system.
- **Generic scope, broadest SAFE default.** What [Allow] remembers is a SCOPE, not only an exact command. Dimensions: *this exact action*; *this kind of action* (a category — read-only shell/file reads, web searches, workspace writes); *this place* (anything of that kind under a folder / project — the learned trusted root is one instance). Tool/launcher families remain CARDSIMPLE-1's mechanism. Default when the owner does not choose: read-only asks → *this kind of action, anywhere*; writes / destructive asks → *this exact action*. The card states in ONE line what was remembered ("Remembered: read-only file reads, anywhere") and offers exactly one narrower alternative ("only here"); never more than two scope buttons. The owner delegated the dimension design to the plan for best UX.
- **Scheduled jobs DO benefit.** A learned decision is projected into the job lane as a DECLARED GRANT — a deterministic lookup by exact effect hash + rails version — never as a classifier call. Decision 0121 keeps "no classifier on autonomous runs"; decision 0153 (learned-decisions-project-into-job-grants) amends its "never consults human-decision memory" clause to "consults it only as a projected declared grant".
- **Inspect and undo.** A `/permissions` view lists learned decisions (scope, when, by whom) with "Forget this"; a re-ask caused by rails-version invalidation states the reason on the card ("Asking again — the safety rules were updated since you last allowed this").
- **Seams (seam map 2026-09-02):** the classifier memory is read after rails fall through (`permission-decision-coordinator.ts:149-200`) and written only after a classifier result (`ipc-permission-classifier-decision.ts:333-366`); the Postgres writer rejects human `allow_once` (`permission-decision-memory-repository.postgres.ts:17-34`) and expiry makes it immediate (`permission-decision-expiry.ts:3-10`) — the human-decision store is a NEW record kind consulted before the classifier, and [Just this once] keeps today's allow_once path. Button labels are central (`channels/permission-interaction.ts:74-88`, rendered by all four providers) and the card's context lines live in `formatPermissionContextLines` (:350-383) — the "Remembered: …" line and the [Allow]/[Just this once]/[No] labels change there, once. The generic scope store REUSES `resolveTrustedRootStage` (`permission-decision-coordinator.ts:219-294`: re-runs rails with each remembered scope, canonicalizes, persists after a remembered approval) — no second root store.

- When a human settles a permission in the interactive `auto` lane with **[Allow]** (remembered) — not with **[Just this once]**, which is never learned — record that outcome keyed by the EXACT effect hash plus the chosen scope (permission-effect-key.ts), as a distinct HUMAN-DECISION record — separate from the existing classifier-verdict cache, which caches machine verdicts, not human outcomes.
- Before consulting the LLM classifier, consult the human-decision memory: an exact-effect match that a human ALLOWED auto-allows with human-decision provenance; an exact-effect match a human DENIED keeps the deny. No match ⇒ fall through to the classifier exactly as today.
- Invalidation: a human-decision record is invalidated when the deterministic rails version bumps (a tightened rule must re-ask) and when its scope inputs change; records are consulted by the interactive auto lane before the classifier; ask mode and auto_strict never consult them; the autonomous lane (scheduled jobs) consults them ONLY as projected declared grants — a deterministic grant lookup, never a classifier call (decision 0153 amending 0121).
- Keying discipline (gap-hunt pass 2): the human-decision key is the EXACT effect hash (raw command/tool/agent/cwd-normalized), NOT the family rule — family keys stay promotion-hint-only, to avoid over-colliding distinct args. This is the ONLY learning path for shapes that can never hold a family grant (runner shims, pipes, generated-runtime commands), so a scheduled job stops asking every run for a command the human already approved.

### 2. Arg-aware native risk before the coarse identity buckets — extends the closed-matrix approach

#### Owner rulings 2026-09-02
- **Attachments are readable, full stop.** Every attachment already present in the conversation (any sender) is readable with zero taps in interactive auto — "it's already there in chat, why need a permission again". Binding (seam map): attachments are read through `mcp__gantry__attachment_open` (`runner/mcp/tools/attachment.ts:38-52`), which takes opaque `gantry_attachment` ids and is validated server-side against the originating conversation/app/account (`jobs/ipc-attachment-open-handler.ts:42-84`) — that validation IS the safety property, so `attachment_open` is birthright in interactive auto. `mcp__gantry__file` (canonical `file`, `admin-mcp-tools.ts:59-97`; actions `list|read|write|promote_scratch`, `runner/mcp/tools/file.ts:12-62`) becomes argument-aware at `gantry-tool-risk.ts:46-49,125-128`: `list`/`read` of artifacts (`artifactId`) or of paths inside unprotected workspace scope → low; `write`/`promote_scratch` judged by PATH; protected/secret paths ask.
- **Workspace file writes are judged by path, not identity.** FileWrite/Edit inside the agent's own workspace folders → low/allow; outside the workspace or into protected state → ask — the same rule the deterministic gate applies to reads.
- **Shared-rails correctness fixes (not widening):** a `2>/dev/null` (stderr) redirect is never a trusted-path candidate (`permission-trusted-paths.ts` pathCandidates); `find` is read-only unless it carries `-delete`, `-exec`, `-execdir` or `-ok` (parser), each proven by adversarial tests.
- **Routing seam (seam map 2026-09-02):** the classifier IS consulted today; what forces the tap is the classifier-ALLOW VETO — a rail ASK signal (`out_of_trusted_root`, unsupported meta-executor) set at `coordinatePermissionDecision` (`application/permissions/permission-decision-coordinator.ts:152-164`) is carried into the IPC tail (`app/ipc-permission-classifier-decision.ts:160-169`, `consultPermissionClassifierBeforePrompt` :248-305) and then vetoes the classifier's allow at :307-308 / :369-401. The change: carry the existing `railSignal` from the rail callback (:111-119) and relax ONLY that veto for interactive auto (`permissionMode === 'auto' && !hostVerifiedJobId` — never `auto_strict`) when the signal is `out_of_trusted_root` or a read-only meta-executor refusal — the classifier's low/medium verdict then stands, with the rail reason attached as provenance. The shared rails (`domain/permission-deterministic-rails.ts:161-228`) are untouched; autonomous runs are excluded by the existing `hostJobId` guard.

#### Live evidence (2026-09-02, ~/gantry/logs/gantry.log + gantry.permission_* — plans/exploration/askfloor-1-runtime-evidence-2026-09-02.md)
In `permission_mode: auto`, ten pure-read shell commands (`ls`, `head`, `wc`, `grep`, `sed -n`, `git log`, `find`) went to a human tap in three minutes because the shared deterministic gate REFUSED them — "Command target is outside the owner-declared trusted roots: …/Workdir" (roots are learned; `~/Workdir` was never learned), "…: /dev/null" (a `2>/dev/null` redirect misread as a target), "Bash meta-executor find is not supported for persistent approval" — and a refusal goes STRAIGHT to ask: no classifier line exists in that window; `deterministic_read_only` decided once in 48 hours. Reading an attachment the owner sent cost three taps (`mcp__gantry__file` classified "can mutate depending on arguments" twice, then the `ls`). 975 of 976 decisions in 48 hours were `allow_once`: taps teach nothing. The judge exists (104 `classifier_verdict` rows in decision memory) but is bypassed for the common case.

What this changes in this section: the refusal itself is the bug, not the rails. In INTERACTIVE auto only (`permissionMode === 'auto'` with no host-verified job id — never `auto_strict`, ask or jobs) a deterministic-gate refusal of a shell command (out-of-trusted-root path, unsupported meta-executor such as `find` without `-exec`) must be routed to the classifier WITH the refusal reason as context, so a read is judged low and allowed and only genuine risk asks — never widening the shared rails (they stay exactly as consulted by the ask/autonomous lanes). Separately, the parser's `2>/dev/null` handling is a plain correctness bug in the shared rails (a redirect to `/dev/null` is never a path target) and is fixed as such.
- The native-risk input consumed at `gantryToolDefaultRisk` becomes ONE small typed DEFAULT-ALLOW table (decision 0155), computed caller-side with host-trusted context, still NEVER widening the shared rails/read-only gate (gap-hunt pass 1 + validation finding 5: rails feed every lane; a global widening would leak to ask/auto_strict/autonomous).
- DEFAULT-ALLOW posture (OWNER RULING 2026-09-03, supersedes the earlier closed browser matrix; decision 0155): in interactive auto every gantry-native tool is LOW by default and auto-allows with typed provenance — ALL `browser_*` actions (status, inspect, navigate, click, type, press, select/fill, evaluate, upload, dialogs, tab lifecycle, screenshot, wait), `file` list/read (entry protection enforced host-side), scheduler and admin READS, attachment tools. Only a CLOSED high-risk list keeps asking: destructive or protected writes (native Write/Edit outside the agent workspace or on protected/secret paths by prospective-write containment; `file` writes to protected virtual paths; a browser `file_attach` with a raw filesystem path outside the workspace, protected or secret — `file_upload` is artifact-based and LOW); scheduler mutations and admin mutations (the registry's canonical exports in `shared/admin-mcp-tools.ts:32-39,129-159,172-177`, imported not restated). Non-own-destination messaging is HIGH by principle; no destination-bearing `send_message` exists today (0052 birthright unchanged; a future variant needs a new decision). Browser network side-effects (navigation, clicks, form submission) are auto-allowed by OWNER RULING 2026-09-03 — decision 0155 amends 0052's browser reading accordingly; 0052's shell-egress and secret floors are untouched. Unknown tools or shapes failing the tool's own schema are `ambiguous` and go to the classifier — never forced HIGH. One small typed risk table with a valid-and-malformed test per row; ask mode, auto_strict and jobs unchanged.
- Grantable-exact un-shadowing (gap-hunt pass 1, finding 3): a `classifyDurableGantryMcpToolName` = `grantable-exact` (routine, boundable) invocation must not be forced HIGH by an earlier coarse identity bucket; its risk is judged on arguments (or routed to the classifier) rather than the tool name.
- Unmapped/known-but-unmapped gantry tools route TO the classifier instead of an unconditional HIGH default (gap-hunt pass 1, findings 1 & 4).
- `file` under the default-allow posture: list/read are LOW rows of the table (the baseline `file` tool satisfies the capability requirement — owner ruling 2026-09-02; it has no capability id and addresses the agent's own artifact store); protection of individual entries is enforced HOST-SIDE in the artifact handler with the scope-aware virtual predicate (list hides protected entries and says how many, read refuses with a fixed non-permission error); write/promote_scratch are judged by destination — inside the workspace LOW, outside/protected/secret HIGH (the "destructive or protected writes" row). Attachments already in the conversation are birthright in every mode (0154).

### 3. Classifier unavailability — NEW (gap-hunt pass 1, finding 4)
- Define and TEST the degraded behaviour when the classifier cannot be reached: fail-closed to ask (never silent-allow), with explicit provenance. Today the await has no local fallback.
- Owner ruling 2026-09-02 — degrade gracefully, never a tap storm: ONE notice per conversation ("My safety judge is offline, so I'll check with you more than usual until it's back"), each card carries a one-line reason, and deterministic read-only proofs (trusted-root reads, learned "kind of action" scopes) still ALLOW without the classifier. Scope: interactive auto only; a scheduled job keeps deterministic denial plus the CARDSIMPLE-2 card recovery.

### Unchanged on purpose
`send_message` stays birthright for complete input (0052; concealed/redacted input keeps its hard-floor ask; a DESTINATION-BEARING variant still requires a NEW decision amending 0052/0121 and is explicitly OUT of scope — arg-awareness here must not silently admit it). The shared deterministic rails/read-only gate, ask mode, auto_strict, the autonomous lane (0121), destructive verbs, the admin-mutation buckets (authority-changing/dispatcher/delegation/decision-actor), scheduler mutations, and the YOLO backstop all keep asking (they are the closed high-risk rows of decision 0155). Family-synthesis machinery is untouched (SHIMPIN-1 owns it).
