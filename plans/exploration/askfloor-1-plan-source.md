# ASKFLOOR-1 — The judge actually judges: context-aware first-asks in auto mode

## Problem
In `permission_mode: auto` the owner meets the permission card for work that needs no human: on 2026-09-02 ten pure reads (`ls`, `head`, `grep`, `sed -n`, `git log`, `find`) cost ten taps in three minutes and reading an attachment the owner had just sent cost three. The live log shows why: the classifier IS consulted, but a deterministic rail ASK signal (`out_of_trusted_root`, "meta-executor find", a `2>/dev/null` misread as a path) **vetoes the classifier's allow** (`app/ipc-permission-classifier-decision.ts:369-401`) and the request goes to a human; `mcp__gantry__file` is rated HIGH by identity (`gantry-tool-risk.ts:46-49`); and 975 of 976 decisions in 48h were `allow_once`, which the memory writer rejects (`permission-decision-memory-repository.postgres.ts:17-34`) — so taps teach nothing. The owner's bar: behave like Claude Code auto mode — reads never tap, the judge decides unknowns, only genuine risk asks, and every human decision is learned. GOVERNING PRINCIPLE (owner, 2026-09-04, verbatim): "The idea is make user experience easier and earn trust over time, not to bug the user every time. Users are needed only when necessary." Every task and grill in this story is measured against it: a tap is a defect unless the action is on the closed high-risk list and has not been decided before.

## Scope / Non-goals
In: (1) interactive-auto veto relaxation so the classifier's verdict stands for rail-refused reads, with the rail reason as provenance; (2) one shared-parser correctness fix (`2>/dev/null` never a path candidate) and one AUTO-ONLY typed signal (read-only `find` — the shared parser stays fail-closed); (3) the DEFAULT-ALLOW posture for gantry-native tools in interactive auto (OWNER RULING 2026-09-03: auto-allow everything, browser included, unless it is on the closed high-risk list — destructive/protected writes, scheduler/admin mutations from the registry's canonical sets; non-own-destination messaging by principle, no such tool today — with the classifier judging anything ambiguous), birthright `attachment_open`, path-judged FileWrite/Edit at the classifier caller; (4) a human-decision memory with a GENERIC scope (exact / kind of action / place) that learns **[Allow]** AND **[No]**, consulted before the classifier in interactive auto only, invalidated on rails-version bump, revocable; (5) LIVE, per-request projection of learned decisions into declared grants for scheduled jobs (decision 0153 amending 0121 — owner ruling 2026-09-02: revocable inputs, never materialized); (6) card UX — **[Allow]** (remembered, default) / **[Just this once]** / **[No]**, a one-line "Remembered: …", one alternative remembering button, the EXISTING `/permissions` command extended with a remembered list + "Forget", and graceful judge-outage behaviour (one process-local notice per conversation per episode; deterministic reads still allow). Out: `send_message` destination semantics (0052/0121), the classifier's internal criteria, ANY widening of the shared deterministic rails EXCEPT the one named input-gated birthright (`attachment_open` of an attachment already in the conversation, owner ruling 2026-09-02), egress policy, package-pinned shim families (SHIMPIN-1), the card lifecycle surface (CARDSIMPLE-2 T2), ask mode / auto_strict / YOLO semantics, cluster-durable outage dedup.
