# ASKFLOOR-1-T4 — Live job projection of learned decisions (0153)

## Context
T3a stores remembered decisions (#484), T3b consults them on interactive auto turns (#486), T3c writes them from a card tap (#488). Jobs still know nothing about them: a scheduled job's IPC request is decided by host policy plus deterministic rails (`runtime/ipc-permission-classifier-decision.ts:75-188`, `reviewedRuleDecision` at `:145` passing `autonomousAllowedToolRules`), and the inline scheduled tail (`app/bootstrap/inline-agent-loop-tools.ts:399-450`) still calls the classifier before converting a miss into a deterministic cancellation — which decision 0121 forbids. Neither job lane carries the job owner: the scheduled `AgentInput` carries a conversation-derived `memoryUserId` (`jobs/execution-phases-run.ts:102,296`) and the inline request omits identity for scheduled runs (`inline-agent-loop-tools.ts:363-376`; `inline-permission-memory.ts:32-42` strips `personId` and marks the lane autonomous). Decision 0153 says a job consumes the owner's learned Allows as ONE deterministic declared-grant input: live, revocable, person-scoped, fail closed; the classifier never runs for jobs; the matched record id is audited. Seam map: `plans/exploration/askfloor-1-t4-seam-map.md`.

## Orchestrator rulings on the seam map's open questions
1. **Where the projection enters (IPC):** at the existing declared-grant seam — `reviewedRuleDecision` (`ipc-permission-classifier-decision.ts:145`) — as one more deterministic input beside `autonomousAllowedToolRules`, with EXACTLY a declared rule's precedence: wherever a declared autonomous rule cannot override a rail today, neither can a projected record; where it allows before rails, so does the projection. No new pre-rail route-guard input; `applyIpcPermissionRouteGuard` (`:272`) keeps sanitising worker risk fields and refusing undeliverable routes unchanged. Reason: the story plan names "learned records as a declared-grant input" and 0153 says "one deterministic declared-grant input"; inventing a second precedence would be a new decision.
2. **Audit key:** the matched record id is stamped as `humanDecisionRecordId` in the `auditMetadata` that `recordDecision` already flattens into `actorContext` beside `jobId` (`application/permissions/permission-management-service.ts:119,489-521`). No port change.
3. **Owner identity:** the job owner is `execution_context.personId` of the JOB ROW, resolved host-side — never a worker-supplied or conversation-derived field. Scheduled lane: `bindActiveJobRun` (`jobs/execution-phases-run.ts:102`) sets a NEW `AgentInput.jobOwnerPersonId` from `currentJob.execution_context.personId` (the same source the inherited tool-policy lookup at `:183` already uses); `memoryUserId` keeps its current meaning and is not repurposed. The inline scheduled request (`inline-agent-loop-tools.ts:363-376`) carries that owner into the projection facts; the IPC lane resolves the owner from the host's job record for the authoritative `hostJobId` (`:75-91`). `null`/blank owner ⇒ no projection (group-created jobs stay owner-less: `job-acting-identity.test.ts:14-58` remains true).
4. **Lookup reuse:** the projection reuses T3b's `findHumanDecision(candidates, railVersion)` (`domain/ports/permission-decision-memory.ts`) with keys from `deriveHumanDecisionScopeKey` (`application/permissions/human-decision-scope.ts:46`) — the identical derivation the interactive lane uses (same effect hash, workspace root, `kindVariant` candidates). It does NOT reuse `runtime/permission-human-memory-stage.ts` (interactive-only lane guard; consulting it would enable interactive semantics on jobs). Only `outcome: allow` rows project; deny rows never project (0153:14); revoked, other-version and other-person rows already never match (`permission-decision-memory-repository.postgres.ts:249-257`).

## Scope / Non-goals
In: ONE application helper that turns (owner, request facts) into a projected declared grant or nothing; the IPC declared-grant seam; the inline scheduled tail (through `inline-permission-memory.ts` or a new small module — the inline file is at 749/750); owner threading in both lanes; the audit stamp in both lanes; the inline suite rewrite; projection-matrix tests. Out: any memory write from a job (0153: jobs never write); card/copy (T5a); `/permissions` (T5b); outage latch (T6); the interactive consult stage; classifier behaviour on interactive lanes.

## Technical Approach
1. One application helper owns the matrix (owner guard, derivation reuse, outcome filter, fail-closed), so both lanes are thin callers and the matrix is pinned once. Rejected: calling `findHumanDecision` from each lane (two copies of the guard chain) or reusing the interactive stage (wrong lane semantics).
2. The projection is a declared-grant INPUT, not a new decision path: the IPC coordinator already reviews declared autonomous rules; the projection joins that review with the same precedence. Rejected: a pre-rail short-circuit (new precedence, new decision).
3. Owner from the job row only (0118, 0153). Rejected: reusing `memoryUserId` (conversation-derived; a job created in a group would project the wrong person's memories).
4. Audit via existing metadata (ruling 2). Rejected: a port change.

## Decisions
0153 (jobs consume projections; live, revocable, person-scoped; audit), 0121 (no classifier on autonomous runs), 0118 (person scope), 0154, 0043. Rulings 1–4 sit in the task plan; none amends a decision.

## Surface Impact
Scheduled and inline jobs owned by a person who remembered an Allow now run that matching call without a card; revoking the row (T5b) or a rails bump stops it immediately. Group-owned jobs unchanged. No schema, migration or UI change.

## Risks
Precedence drift: the projection must inherit, not define, declared-rule precedence (pinned by the non-overridable-rail test). Owner leak: any conversation-derived identity reaching the projection widens to the wrong person (pinned by the group-job null-owner tests in both lanes). Ceilings: three touched files near their ceilings; the helper absorbs the logic. Lane leak: the interactive stage must stay interactive-only (no change to it; the inline interactive tests stay green).
