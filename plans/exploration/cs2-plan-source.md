# CARDSIMPLE-2 — One canonical card: fold the setup-pause prompt into the job permission card

## Context
Today a blocked scheduled job can surface TWO parallel things: the `job_permission_card` (the multi-need aggregate) and a separate "Setup needed" prose card built by `setup-pause-permission-prompt.ts`. The prose card doesn't settle or retract like a chat permission card — the live incident (KnackLabs Lead Maintenance) showed a stale "Setup needed" card lingering on a job that was actually running, its "Retry" a no-op. CARDSIMPLE-2 makes the job permission card the ONE actionable surface for every blocked need, on all four providers, that settles/retracts like the Telegram permission card. CARDSIMPLE-1 (family grants) already shipped; this is the card-unification slice only. Requirements grill + plan grill (sol@xhigh, 2026-09-01) findings folded.

## Contract (CARDSIMPLE-2 ACs — confirmed spec "One canonical card" + AC1, extended by the grills)
- ONE actionable surface — the canonical `job_permission_card` — for every reachable blocked-need combination (action-shape `approve_grant|fix_proposal|instruction` × blocker-type tool/credential/browser/MCP/local-CLI; compound = RunCommand content case) and every pause cause, on all four providers. No "Setup needed" prose; non-approver routes receive nothing; `notified_fingerprint` owned by card delivery; the reconciler does not loop on unnotified pauses; no second actionable surface while the sole card is established/pending.
- RULING 1: instruction / fix_proposal rows AUTO-RETRACT on a passing readiness re-check. TWO affordances — `Apply` on fix_proposal, `Recheck` on instruction. NO Dismiss: a card leaves ONLY when the blocker actually clears (auto, or via Recheck), so a real blocker is never hidden. Retirement also fires when the job goes silent/non-paused, is deleted/disabled, becomes ready, or changes fingerprint.
- RULING 2: a job's real state is authoritative over stale `setup_state` — a `ready` readiness result OR a running job atomically clears/replaces stale setup_state and idempotently retracts the canonical card on ANY readiness pass, via the SHARED readiness-result commit path (not only setup-paused recovery).
- Preserved: 0144 denied-row Reconsider; 0134 pipe/per-leaf/once; the `transient_permission` receipt; 0124 bounded delivery + operator/owner-initiated post-exhaustion recovery.
- Green: unit + Postgres integration suites, tsc, check:architecture.

## Steps
1. **Single canonical identity; delete the parallel lifecycle.** `raiseSetupPausePermissionPrompt` (`application/jobs/setup-pause-permission-prompt.ts:71`) stays the sole ingress but projects blocked needs straight into the EXISTING `job_permission_card` aggregate under ONE canonical card identity. `setupFingerprint` is reduced to a row generation/dedupe key only — NOT a second card identity. Delete the setup-specific preparation/selection/cancellation/identity machinery (`:103-119`, `:122-146` first-reviewable selection, `:150-217`, `:220-256`). When a live-run card already exists, setup rows merge into that card (see owner ruling). Card creation must be independent of a live run lease: remove the live-run/lease attachment requirement (`app/bootstrap/job-permission-durability-wiring.ts:215`) so a setup pause with NO live run still creates/attaches the canonical card (spec: creation is setup-fingerprint-backed — covers creation-time, preflight, final-setup, denial/timeout, partial-recovery pauses).
2. **Every blocker is a row, actioned through the EXISTING card envelope.** Remove the first-reviewable narrowing entirely; render every blocker as a row by action kind. `Apply` (fix_proposal) and `Recheck` (instruction) and the compound-row `scheduler_retry_ask` are carried on the EXISTING permission-card action envelope — its four-provider serialization, approver authorization, and fingerprint/generation binding + dispatcher — NOT a new codec. Add end-to-end action tests (tap → handler → readiness re-check → retract) per action kind on all four providers, INCLUDING the negative path: a FAILED Apply or a STILL-BLOCKED Recheck preserves the row + card + durable identity (never hidden — per RULING 1). Pipes stay reformulation-only; safe compounds per-leaf.
3. **notified_fingerprint from 0124 persisted state (no new field).** Card delivery owns the `notified_fingerprint` write. Derive established/pending/exhausted from 0124's EXISTING persisted item/generation state — NOT from the transient `raised|already_pending` call result (a later reconciler pass cannot see that). Delete the prose send + its `markJobSetupNotified` call (`jobs/execution-readiness.ts:245`); the persisted "sole card established/pending" state suppresses the setup-terminal send and closes the unnotified-reconciler loop; non-approver routes get nothing.
4. **Auto-retract in the shared readiness-commit path (RULING 2).** Place ready/running stale-`setup_state` clearing + idempotent card retraction in the SHARED readiness-result commit path so it fires on run-start and reconcile for running/non-paused jobs — not merely by relaxing the `isSetupPausedJob` inner guard (`application/jobs/job-permission-recovery.ts:117`). A targeted `Recheck` routes through that same commit path. Delivery settles idempotently AFTER committed state. This shared retirement point owns ALL of RULING 1's retirement triggers (replacing the deleted setup-specific cancellation): ready, running/non-paused, job deleted/disabled, and setup-fingerprint change all retract the canonical card idempotently. Test each of the deleted/disabled and fingerprint-change cases explicitly.
5. **Surface constraints (deletion).** No setup prose on any route; card only on the approver route. Delete the CARDFIX-1 prose-card affordance layer (`setupStoryActionAffordances` + the `MessageActionAffordance` variant + callback parsing + four provider codec branches) and the Pause-job button/kind/codecs. KEEP `scheduler_pause_job` MCP task/IPC handler/risk/tests and the #462 interactive host-provenance lane. The replacement action path is step 2's existing envelope.
6. **Delivery authority unchanged.** 0124's persisted prompt-identity + item/generation state stays the delivery authority; no new delivery state machine; bounded retries + terminal outcomes preserved; post-exhaustion recovery is operator/owner-initiated (NOT reconciler-driven), re-delivering under the SAME durable identity.
7. **Reuse `formatSchedulerSetupStory`** as the canonical card-body/row projection (spec-mandated content parity — not optional).
