# CARDSIMPLE-2-T1 — Surface unification: one canonical card

## Problem
A blocked scheduled job surfaces two parallel things — the canonical `job_permission_card` aggregate and a separate "Setup needed" prose card (`setup-pause-permission-prompt.ts` + the prose send in `execution-notifications.ts`). The prose card has its own identity/lifecycle and does not settle/retract like a chat permission card (live stale-card incident). T1 folds the setup path into the one canonical card, makes card creation independent of a live run, moves `notified_fingerprint` ownership to card delivery, and deletes the setup-EXCLUSIVE prose surface — without touching the shared scheduler affordances that recovery/run-again cards also use.

## Scope / Non-goals
In (T1): projection of setup rows into the canonical card under one identity; remove the live-run/lease creation dependency; `notified_fingerprint` from 0124 persisted state; delete the setup-exclusive prose sender + `setupStoryActionAffordances`; reuse `formatSchedulerSetupStory`. Out (T2, depends on T1): the readiness-commit retirement lifecycle (auto-retract, RULING 1/2), `Apply`/`Recheck` row actions, four-provider action e2e. Hard non-goal: do NOT delete the shared `scheduler_pause_job`/`scheduler_run_now`/`scheduler_retry_ask` kinds or their four provider codecs — recovery + run-again cards depend on them. Scope-disjoint from the CARDSIMPLE-1 grant files.

## Acceptance Criteria
- CS2-T1-AC1: one canonical `job_permission_card` identity (`jobPermissionCardId(appId, jobId)`) is the only actionable surface for every reachable blocked-need combination and every pause cause (with or without a live run) on all four providers; no "Setup needed" prose is sent; non-approver routes receive nothing; no second actionable surface while the sole card is established/pending.
- CS2-T1-AC2: `notified_fingerprint` is owned by card delivery and derived from 0124's existing persisted item/generation state; the reconciler does not loop on unnotified pauses.
- CS2-T1-AC3: the setup-exclusive prose sender + its `markJobSetupNotified` path and `setupStoryActionAffordances` are deleted with zero-reference grep gates; the shared scheduler affordance kinds/codecs, `scheduler_pause_job` MCP/IPC/risk/tests and the #462 interactive host lane are retained.
- CS2-T1-AC4: existing unit + Postgres integration suites, tsc and check:architecture green.

## Technical Approach
1. **One identity (project new; defer legacy-identity deletion to T2).** In `application/jobs/setup-pause-permission-prompt.ts`: `raiseSetupPausePermissionPrompt` (:71) projects blocked needs into the existing card via `job-permission-card-projection.ts` under `jobPermissionCardId(appId, jobId)` (`job-permission-durability-state.ts:32`). Delete the first-reviewable selection (:128-148) — project ALL blockers as rows; `setupFingerprint` becomes a row dedupe/generation key mapped to row identity. T1 STOPS MINTING the `setup-pause:<job>:<fingerprint>` identity for new cards but does NOT delete `setupPausePermissionRequestId` (:237) / `retireSetupPausePermissionPrompt` (:220) — T2 owns retirement/cancellation and removes the legacy seam then (grill finding 2: deleting it in T1 dangles the retained cancel + T2 retire callers). T1 adds a zero-reference gate proving no NEW mint of the old identity. Rewire raise callers: `setup-pause-permission-wiring.ts` (:143/:356/:385/:389), `runtime-services-permission-card.ts` (:78), `job-permission-recovery.ts` raise (:267) — retire (:162) is T2.
2. **No live-run/lease dependency — dedicated setup-origin branch.** In `app/bootstrap/job-permission-durability-wiring.ts`: add a SETUP-ORIGIN, WAITER-FREE `attachRequest` branch that creates/attaches the card WITHOUT run/lease fields and without minting a waiter or delivering a waiter response (grill finding 3: merely relaxing the :216-224 guard still builds a run/lease waiter). Keep the existing guarded live-run branch (:216-249) unchanged; a live-run card merges setup rows into the same `jobPermissionCardId` identity. Map `setupFingerprint` to row identity/dedupe, not just snapshot it.
3. **notified_fingerprint from persisted state — define the reader.** In `jobs/execution-readiness.ts` (`notifyJobSetupRequired` :160): delete the prose send branch (:221-231) and the `markJobSetupNotified` write (:245-248). ADD a persisted-state read (grill finding 4: the function has no 0124-state reader today; raised/pending currently returns `notified=false` while terminal suppression needs established=true) — query the card's 0124 item/generation state via `canonical-job-target-state.ts` and return exact established/pending semantics; card delivery ALONE performs the `notified_fingerprint` CAS. The persisted "sole card established/pending" state suppresses the setup-terminal send (`execution-notifications.ts:396`); non-approver routes get nothing. Confirm the reconciler (`setup-permission-prompt-reconciliation.postgres.ts`) no longer loops on unnotified pauses.
4. **Delete the setup-exclusive prose surface.** In `application/jobs/scheduler-setup-story.ts`: delete `setupStoryActionAffordances` (:53-85); KEEP `formatSchedulerSetupStory` (:20) and reuse it as the canonical card body/row projection. In `jobs/execution-notifications.ts`: remove the setup path `notifySchedulerSetupRequired` (:241) and its `setupStoryActionAffordances` call (:277). RETAIN `recoveryActionAffordances` (:159) and `runAgainActionAffordances` (:177) and the shared kinds/codecs untouched.

## Decisions
Load-bearing: 0124 (persisted delivery state reused for notified_fingerprint + sole-card signal), 0127 (tagged setup-action model), 0106 (no job mutation), 0128 (approval result). No new decision. The shared-affordance retention is a surface-map correctness constraint, not a decision change.

## Surface Impact
User-visible: a blocked job shows ONE card (no separate "Setup needed" prose); non-approver routes see nothing. Removed: the setup prose message + `setupStoryActionAffordances` (the setup card's Retry/Pause buttons). Unchanged: recovery/run-again cards keep their `scheduler_*` buttons (shared codecs retained); `scheduler_pause_job` MCP/IPC/risk retained.

## Task Decomposition
Single task (T1). T2 (lifecycle + actions) depends on it. Zero-reference grep gates for: the deleted prose sender, `markJobSetupNotified` setup path, and `setupStoryActionAffordances`.

## Risks
Dangling callers after deleting `setupStoryActionAffordances`/prose sender; accidentally deleting a SHARED codec/kind (breaks recovery cards — the map's key hazard); a route still sending prose; the reconciler still keyed on the old notified marking. Mitigation: grep zero-reference gates; `provider-affordance-parity` + `scheduler-message-actions` + `execution-notifications` suites must stay green (they exercise the shared codecs).
